# 限流实施方案（Rate Limiting Implementation）

## 范围

本次只做**限流**，不做熔断（熔断单独一份方案，后续再排）。落地目标服务：**dispatch**（`SubmitTask`、`CancelTask`）和 **telemetry**（`IngestTelemetry`、`QueryAggregation`、`GetFleetSnapshot`）——对应 discussion 里"Optimization 定时轮询读 telemetry + 高频调 dispatch"这个具体风险点。resource/gateway/alarm 不在本次范围，中间件做成通用能力后它们可以用同样模式自行接入。

## 架构决策（已调研确认）

- **挂在 `internal/platform/decorator/`**，不是 gRPC server 全局 interceptor：因为限流阈值需要按 operation 类型区分（`SubmitTask` 应比 `GetTask` 更严格），decorator 已经是协议无关、按 handler 类型区分的统一入口，全部 ~50 个 CQRS handler 都走这里。
- **粒度**：v1 按 operation 类型（每个 handler 一个独立 `*rate.Limiter`），不做 per-tenant（已确认）。
- **默认关闭**：所有改动 additive，未显式在 config 里 `enabled: true` 的 handler 行为完全不变。

## 1. 新增中间件：`internal/platform/decorator/ratelimit.go`

```go
package decorator

import (
	"context"
	"errors"

	"golang.org/x/time/rate"
)

// ErrRateLimited is returned when a handler's rate limiter has no tokens left.
// Adapters must map this to a "too many requests" transport status
// (gRPC codes.ResourceExhausted / HTTP 429).
var ErrRateLimited = errors.New("decorator: rate limit exceeded")

// WithRateLimit rejects a request once limiter.Allow() reports no tokens.
// One *rate.Limiter = one bucket for whatever scope the caller chose
// (v1: one limiter per handler type, constructed at wiring time).
func WithRateLimit[C, R any](limiter *rate.Limiter, metricsClient MetricsClient) Middleware[C, R] {
	return func(next Handler[C, R]) Handler[C, R] {
		return handlerFunc[C, R](func(ctx context.Context, in C) (R, error) {
			if limiter != nil && !limiter.Allow() {
				if metricsClient != nil {
					metricsClient.Count("ratelimit", generateActionName(in), "rejected")
				}
				var zero R
				return zero, ErrRateLimited
			}
			return next.Handle(ctx, in)
		})
	}
}
```

## 2. 用 functional options 扩展 `apply.go`，不破坏现有 ~50 个调用点

新增 `internal/platform/decorator/options.go`：

```go
package decorator

import "golang.org/x/time/rate"

// Option configures optional decorators for Apply*Decorators. Zero value
// (no options passed) preserves today's behavior exactly.
type Option[C, R any] func(*decoratorConfig[C, R])

type decoratorConfig[C, R any] struct {
	rateLimiter *rate.Limiter
}

// WithRateLimiter enables rate limiting for this handler. Pass nil (or omit
// the option entirely) to leave rate limiting disabled.
func WithRateLimiter[C, R any](limiter *rate.Limiter) Option[C, R] {
	return func(c *decoratorConfig[C, R]) { c.rateLimiter = limiter }
}
```

改 `apply.go`（在 `Logging` 之后、`Metrics` 之前插入限流——被拒绝的请求仍进访问日志，但不再产生 Metrics 耗时统计/Tracing span）：

```go
func ApplyCommandDecorators[C, R any](handler CommandHandler[C, R], metricsClient MetricsClient, opts ...Option[C, R]) CommandHandler[C, R] {
	cfg := &decoratorConfig[C, R]{}
	for _, opt := range opts {
		opt(cfg)
	}
	mws := []Middleware[C, R]{WithLogging[C, R]("command")}
	if cfg.rateLimiter != nil {
		mws = append(mws, WithRateLimit[C, R](cfg.rateLimiter, metricsClient))
	}
	mws = append(mws, WithMetrics[C, R]("command", metricsClient), WithTracing[C, R]("command"))
	return Chain(handler, mws...)
}
// ApplyQueryDecorators mirrors the same change.
```

变参 `opts ...Option[C, R]` 是纯加法：现有 resource/gateway/alarm/dispatch/telemetry 里所有不传 `opts` 的调用点无需任何改动即可编译通过。

## 3. 依赖

`internal/platform/go.mod` 新增 `golang.org/x/time`（`go get golang.org/x/time/rate` 后 `go mod tidy`）。因为 dispatch/telemetry 各自是独立 module（`replace` 指向 `../platform`），它们的 `go.sum` 也需要跟着更新（`go mod tidy` 各跑一次）。

## 4. 接入 dispatch（`SubmitTask`、`CancelTask`）

- `internal/dispatch/options/options.go`：`DispatchOptions` 新增 `RateLimit RateLimitOptions`；

```go
type RateLimitOptions struct {
	SubmitTask RateLimitRule `mapstructure:"submit-task"`
	CancelTask RateLimitRule `mapstructure:"cancel-task"`
}

type RateLimitRule struct {
	Enabled bool    `mapstructure:"enabled"`
	RPS     float64 `mapstructure:"rps"`
	Burst   int     `mapstructure:"burst"`
}
```

- `internal/dispatch/config/config.go`：新增一个 `newLimiter(rule options.RateLimitRule) *rate.Limiter`（`!Enabled` 返回 `nil`），解析进 `Config`。
- `internal/dispatch/server.go`：从 `cfg` 构造 `submitTaskLimiter`/`cancelTaskLimiter`，传入 `application.Dependencies`（新增两个可选字段，nil = 不限流，和现有 `Metrics` 字段"可传 nil 禁用"的约定一致）。
- `internal/dispatch/application/app.go`：把 `Dependencies.SubmitTaskLimiter` 传给 `command.NewSubmitTaskHandler(...)` 新增的可选参数。
- `internal/dispatch/application/command/submit_task.go` / `cancel_task.go`：构造函数签名末尾加 `opts ...decorator.Option[SubmitTask, *SubmitTaskResult]`（变参，现有调用点/测试不受影响），内部 `decorator.ApplyCommandDecorators(handler, metricsClient, opts...)`。
- `internal/dispatch/adapter/inbound/grpc/errors.go` 的 `toGRPCError`：新增一条

```go
case errors.Is(err, decorator.ErrRateLimited):
    return status.Error(codes.ResourceExhausted, err.Error())
```

- `config/dispatch.yaml`：新增（默认关闭）：

```yaml
dispatch:
  rate-limit:
    submit-task:
      enabled: false
      rps: 50
      burst: 100
    cancel-task:
      enabled: false
      rps: 20
      burst: 40
```

## 6. 测试

## 不在本次范围内（明确延后）

- 熔断（Circuit Breaker）——单独一份方案。
- resource/gateway/alarm 接入限流——中间件通用，留给需要时按同样模式接入。
- per-tenant 限流隔离——已确认 v1 不做。
- Optimization 自身作为调用方的客户端侧限流/背压——等 Optimization 设计时再定。
