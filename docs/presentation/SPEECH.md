## 0. 开场（1 min）

大家好，今天想和大家系统地讲一遍我们这套 **VPP（虚拟电厂）中台服务**。

背景先交代一下：这套系统目前已经有 **8 个业务服务**（外加 1 个所有服务共用的 `platform` 公共库，很多时候大家会把它也算成"第 9 个"，因为它体量不小，是整套系统的地基），基础设施基本搭建完成，几条主链路都已经跑通。

但这些代码**几乎全部由 AI Agent 辅助完成**——功能是有了，但作为负责人，我自己还没有从头到尾、系统性地梳理过"这套系统到底是怎么回事"。所以接下来一段时间，我不打算再堆新功能，而是要做三件事：**理清架构、做测试、找问题**。

今天这次分享，就是"理清架构"的第一步产出——先把宏观的业务逻辑和服务关系讲清楚，讲到"别人听得懂、我自己也想明白"的程度。技术细节和亮点，我们后面再一步步补。

## 1. 什么是 VPP，为什么需要这套中台（3 min）

**VPP = Virtual Power Plant，虚拟电厂。**

一句话解释：把大量分散的、单体规模很小的电力资源（储能电池、光伏、可调节负荷等）用软件"捏合"成一个逻辑上统一的整体，让它们**像一座大电厂一样**被管理、被调度、参与电网互动。

背后的矛盾很直接：

- 电网/能源市场习惯打交道的对象是"大电厂"这种量级的资源；
- 但分布式资源天生又小又散——一个小区的储能柜、一片屋顶光伏，单独拎出来都不够格上牌桌。

所以中间需要一层"中台"，把"一堆散的"变成"一个整的"。这层中台要解决的问题，拆开看正好对应我们后面要讲的各个服务：

| 要解决的问题 | 对应服务 |
|---|---|
| 这个虚拟电厂里到底有哪些资源？怎么组织？ | **Resource** |
| 不同厂商、不同协议的设备，怎么说"同一种语言"接进来？ | **Gateway** |
| 设备现在是什么状态？历史数据存哪、怎么查？ | **Telemetry** |
| 什么时候该充、该放、该调？ | **Optimization / Forecast** |
| 决策怎么变成对设备的真实动作？ | **Dispatch** |
| 出问题了怎么第一时间知道？ | **Alarm** |
| 没有真设备之前，怎么把上面这些都跑起来验证？ | **Simulator** |

**一句话总结这套中台的价值：** 让一堆分散、异构的小型电力资源，在软件层面看起来、用起来像一个可管理、可调度、可预测的整体。

## 2. 系统全景一张图（3 min）

> 🖼 切到 [`01-service-overview.excalidraw`](./diagrams/01-service-overview.excalidraw)

整体分五层，自上而下看：

1. **最外层：进来的人和设备**——现场设备/EMS，运维管理端，还有负责签发身份的 Casdoor。
2. **统一大门：APISIX**——所有从外面进来的请求，不管是设备上报数据还是人在操作后台，都先过这一道关卡，统一做身份核验、路由、限流。
3. **核心业务服务层**——Resource、Gateway、Telemetry、Dispatch 四个服务撑起主链路。
4. **智能 + 告警层**——Optimization（自动决策）、Forecast（预测）、Alarm（告警）三个服务在主链路之上做增值。
5. **最底层：事件总线与存储**——Kafka 负责服务之间"发生了什么"的异步通知；每个服务有自己独立的 Postgres 库，互不越界查表。

**关键设计感受（先埋个伏笔，第 9 章会展开）：** 这不是一个大单体应用堆功能，而是**一个服务只回答一个问题**的微服务群；服务之间能用事件解耦的，就不用同步调用硬绑在一起。

## 3. 服务巡礼（7 min）

逐个过一遍每个服务：一句话定位 + 核心职责 + **刻意不做什么**（边界感本身就是设计的一部分，值得强调）。

### Resource —— 资产台账

**回答的问题：这个 VPP 里有什么设备？**

维护一棵四级资源树：`场站 Site → 资产 Asset → 可控单元 CU → 测点 Point`。所有 CRUD、树操作、批量导入都在这里。**不负责**：外部系统怎么接入、设备用什么协议、连接状态好不好——那些是别的服务的事。

### Gateway —— 协议网关 / 外部系统适配器

**回答的问题：外部世界的"张三"对应我们平台内部的哪个资产？数据/指令怎么翻译？**

核心是"设备映射"：把外部系统的 ID、协议，翻译成平台内部统一认的 `CUCode`。数据进来时"归一"，指令出去时"适配"。**不负责**：资产本身的业务属性，也不负责调度编排逻辑。

> 注：这个名字容易让人误会成"所有对外流量的统一网关"，实际上它专精"EMS/外部系统适配"这一件事，管理端访问 Resource、Dispatch 从来不经过它。这是现状盘点章节会提到的一个"措辞容易引起误解"的点。

### Telemetry —— 遥测中心

**回答的问题：设备数据存哪？怎么查历史？现在是什么状态？**

三件事：写时序数据库（历史全都在）、维护一份"最新状态快照"（供实时查询，不用每次都扫历史表）、发现"状态跳变"时对外广播一个事件（比如开关量从"合"变"分"）。**不负责**：任何和资产业务含义相关的判断，也不知道 Resource 的存在。

### Dispatch —— 调度执行引擎

**回答的问题：一个控制意图怎么拆解、怎么执行、失败了怎么办？**

把一个"任务"拆成若干"动作"，动作再拆成一条条"命令"，按顺序或并行执行，处理超时重试和失败熔断。**不负责**：协议转换（那是 Gateway 的事），也不知道设备到底是模拟的还是真实的。

### Simulator —— 虚拟设备沙盘

**回答的问题：没有真实设备时，怎么让整条链路依然真实地跑起来？**

一组"活的"虚拟设备：会随时间自然变化（比如电池 SOC 缓慢下降），会响应控制指令，还能人为注入故障（离线、拒绝指令、上报延迟）。它站在 Gateway 对面，扮演"外部系统"的角色。**不负责**：资产权威定义（配置从 Resource 只读拉取，不自建一套）。

### Alarm —— 告警中心

**回答的问题：出问题了，怎么变成一张"看得见、能处理"的工单？**

只"听"两类信号：任务失败（来自 Dispatch）、测点异常跳变（来自 Telemetry）。同一个问题在解决之前会自动合并成一张单（不刷屏），支持认领、关闭。**不负责**：全量审计、复杂规则引擎、自动恢复。

### Optimization —— 自动决策（规则版）

**回答的问题：现在该不该动？动多少？**

一个"定时闹钟"：每隔固定时间醒来看一眼 Telemetry 的最新状态，命中预设阈值规则（比如电池电量太低）就自动生成一个调度任务丢给 Dispatch。**目前是规则引擎，不是智能优化算法**，也还没接上真正的预测数据。

### Forecast —— 预测分析

**回答的问题：接下来一段时间，负荷/出力大概会怎么走？**

另一个"定时闹钟"：定期回看 Telemetry 的历史数据，用移动平均、同比这类朴素算法，算出一批"未来预测点"存起来，对外提供只读查询。**目前还没有真正的调用方**——相当于弹药先造好，还没往枪里装。

### platform —— 公共地基（不是独立服务）

严格说不算"业务服务"，但值得单独提一句：统一鉴权、统一可观测埋点、统一事件信封、统一 ID 生成……都沉淀在这里。所有服务长得像、读起来有共同的套路，就是因为共用了这一个地基。

**一句话记住全部分工（口诀）：**

> Resource 定义"有什么"；Gateway 负责"内外身份与通道"；Telemetry 负责"记下来"；Dispatch 负责"让它去做"；Optimization / Forecast 负责"想清楚该怎么做"；Alarm 负责"出事了喊人"；Simulator 负责"没有真设备时让这一切依然真实地跑起来"。

## 4. 业务闭环一：遥测怎么采上来（3 min）

> 🖼 对照 [`02-business-loop.excalidraw`](./diagrams/02-business-loop.excalidraw) 中 ①②③ 部分

```
设备 / Simulator ──上报──▶ Gateway ──翻译成内部身份──▶ Telemetry
                                                          ├─ 写历史（时序库）
                                                          ├─ 更新"最新状态"快照
                                                          └─ 发现跳变 → 广播事件
```

打个比方：**Gateway 像"翻译官 + 门卫"**——外面的客人各种口音都有（不同外部系统、不同协议），先在门口翻译成平台自己的"普通话"（也就是内部统一的 `CUCode`），再往里传。

**Telemetry 像"中央档案室 + 实时看板"**：历史数据全部归档（时序库），但如果每次都翻档案柜找"现在几点了"太慢，所以另外维护一面"看板"（快照），谁问"现在这台设备什么状态"，直接看板上读，不用翻档案。

## 5. 业务闭环二：指令怎么下发下去（3 min）

> 🖼 对照业务闭环图中 ④⑤ 部分

```
管理端 / Optimization ──提交任务──▶ Dispatch
                                       │ 拆成 动作 → 命令
                                       ▼
                                    Gateway ──▶ 外部设备 / Simulator
```

有一个很重要的设计点：**"同步受理 + 异步终态"**。

设备真正执行一条指令，可能需要几秒到几十秒，如果 Dispatch 傻等这个结果，整条链路就会被"卡死"。所以实际流程是：Dispatch 把指令交给 Gateway 后，Gateway **立刻**回一句"我收到了，正在处理"，然后转身去异步执行；真正执行完成后，再通过事件（不是原路返回）通知 Dispatch"这条指令成功了/失败了"。

**打个比方**：这就像点外卖——下单后骑手不会一直在电话里跟你说话直到送到，而是先给你一个"已接单"的确认，送到后再给你一条完成通知。

**失败怎么办：** 目前采用"一票否决"策略——一个任务里只要有一条命令失败，就立刻取消这个任务里其他还没执行的动作，整个任务标记失败，不做自动的"补偿回滚"。宁可让人介入，也不在设备控制上自作主张地"自动纠错"。

## 6. 业务闭环三：平台怎么自己"思考"（4 min）

> 🖼 对照业务闭环图中的 Optimization/Forecast 部分

这一部分是让系统从"你让它做什么它做什么"往"它自己知道该做什么"迈的第一步，但目前还是**很朴素的版本**，讲的时候要如实说清楚"到了哪一步"。

**Optimization（决策）**：像一个每隔一分钟醒一次的闹钟。醒来就问 Telemetry "现在状态如何"，套一个简单的阈值规则（比如"电量低于 20% 就该充电了"），如果触发，自动拼一个调度任务发给 Dispatch。是"规则引擎"，不是"智能优化算法"或"AI 决策"。

**Forecast（预测）**：另一个闹钟，间隔更长（比如 15 分钟）。醒来后回看 Telemetry 里过去一段时间的历史数据，用两种朴素算法（移动平均 / 同比）猜"接下来会怎样"，把结果存起来，对外提供"查一下下一个预测点是多少"的接口。

**这两者目前还没有接上**——Optimization 理论上应该参考 Forecast 的预测结果来做更聪明的决策，但目前这条线还是一个"占位符"，没有真正打通。之所以先把两个服务独立做出来、接口先定好，是为了以后想换更真实的算法（甚至上机器学习模型）时，只需要在这两个服务内部替换实现，不用去动 Dispatch、Telemetry 这些下游服务的任何代码。

## 7. 业务闭环四：出问题怎么发现（3 min）

> 🖼 对照业务闭环图中的 ⑥ Alarm 部分

Alarm 更像一个**消防站**，而不是"巡逻队"——它自己不会主动去检查每个设备哪里有问题，而是"支起耳朵"听两类广播：

1. Dispatch 广播的"任务失败了"；
2. Telemetry 广播的"某个测点数值跳变了"（比如开关状态突然变化）。

**合单逻辑很关键**：同一个问题在没被解决之前，不会每次发生都开一张新单刷屏，而是**累加在同一张工单上**（次数 +1），运维人员认领（Ack）、处理完关闭（Close）之后，下次再发生才会开新单。这个设计的意义是——控制"信息噪音"，让运维真正能看得过来。

**目前的边界（如实讲）**：只认这两类信号源，没有更复杂的规则 DSL，没有自动恢复能力，管理端目前是直接连接 Alarm、还没经过统一网关。这些都是有意识的"先把主干做对，细节以后补"的取舍，不是遗漏。

## 8. 一个资产从 0 到能被调度（3 min）

这一节串一下"新增一个设备"的完整流程，帮大家建立一个具体的心智模型：

```
① 管理端在 Resource 里新建一个 CU（登记这个设备，拿到一个全局唯一 ID）
② 管理端再去 Gateway 建立"映射"（告诉平台：这个 ID 对应外部系统的哪个具体设备/地址/协议）
③ 之后，这个设备的遥测和控制指令就都能通了
```

**这里有一个刻意的设计：这两步是分开的、由管理端人工/流程串起来，Resource 和 Gateway 两个服务互相并不知道对方的存在。**

为什么不做成"建完资产自动建好映射"？因为建映射需要知道"这个设备接的是哪个外部系统、外部 ID 是多少"，而这个信息在资产刚创建的那一刻，往往还不知道——设备可能几天后才真正联网接入。所以创建这一步，故意不做自动化，交给上层的管理流程去协调。

**反过来，删除是自动的**：如果一个设备在 Resource 里被删除或禁用，Gateway 会通过事件自动收到通知，自动把对应的映射关系停用，不需要人再去手动点一下。

一句话记住这个不对称设计：**创建需要人工协调（信息还不全），删除可以自动清理（信息已经足够）。**

## 9. 架构设计理念（5 min）

这一节讲"为什么这么设计"，不深挖代码，但要让人感受到这套系统是**有意为之**的，不是随手堆出来的。

1. **单一职责，边界清晰**：每个服务只回答一个问题（回顾第 3 章的表格）。好处是改一个服务时，不用担心"牵一发动全身"。
2. **能异步解耦就不同步硬绑**：服务之间凡是"通知类"的信息（比如"设备被删除了""任务失败了"），都通过事件（Kafka）广播，而不是让一个服务直接打电话给另一个。这样一个服务临时挂了，不会像多米诺骨牌一样连锁拖垮别的服务。
3. **内部分层套路统一**：每个业务服务内部都遵循同一套"接口层 → 业务编排层 → 核心业务规则层 → 存储实现层"的写法（业内称为"六边形架构"）。好处是学会看一个服务的代码，其它服务基本也能看懂，降低认知成本。
4. **看和做分开（CQRS）**：查询数据的代码路径和修改数据的代码路径是分开的，互不干扰，查询可以尽量做得快和灵活，修改可以尽量做得严谨。
5. **统一大门**：所有对外请求先过 APISIX 这一个关卡做身份核验和限流，业务服务自己不用重复操心这些"门卫"逻辑。
6. **关键组件可插拔**：比如"外部系统怎么对接"、"预测用什么算法"，都被设计成可以整体替换的插件，不需要为了换一个算法或对接一个新外部系统，去动核心业务逻辑。

## 10. 认证鉴权一分钟版（2 min）

一句话打比方讲清楚三个角色：

- **Casdoor** 像"公安局"：管你是谁、发身份证（登录、签发令牌）。
- **APISIX** 像"进城关卡"：所有请求进城门之前，先在这里查一下身份证是不是真的。
- **每个服务自己内部还有一个"门卫"**（本地缓存的权限规则），决定"你这个身份能不能干这件事"，不需要每次都跑去问公安局——这样即使公安局临时联系不上，城门也不会直接瘫痪，只是变得**更谨慎**（宁可拒绝也不放行），尤其是涉及直接操作物理设备的 Dispatch，这块卡得比查资产信息更严。

这块目前的角色划分（管理员/操作员/查看者）还是占位性质，真实的业务角色体系还没最终定下来，但不影响现在先用这套框架跑起来。

---

## 11. 可观测性三件套（2 min）

系统健康怎么知道？三个维度，各管一段：

| 维度 | 回答的问题 | 落地工具 |
|---|---|---|
| **链路追踪（Traces）** | 这一次请求经过了哪些服务，卡在哪一跳？ | Jaeger |
| **指标（Metrics）** | 现在 QPS、错误率、延迟怎么样？ | Prometheus + Grafana |
| **日志（Logs）** | 具体发生了什么，哪一条报错？ | Loki + Grafana |

三者是打通的：日志里带着"链路 ID"，点一下就能跳到对应的链路追踪图，方便"从一条报错日志一路查到是哪个服务的哪一跳出的问题"。

---

## 12. 现状盘点（3 min）

**已经做到的：** 8 个服务都能独立编译、通过单元测试；遥测采集、控制下发、告警联动这几条主链路都已经打通；本地已经能用 Kubernetes（kind）方式整体部署，CI/CD、集成测试也已经具备。

**故意没做的（不是漏掉，是明确的取舍）：**

- 真正复杂的电价/负荷预测算法（超出当前阶段目标，先用朴素算法把接口和数据形状定好）
- 真实 EMS 设备对接（目前没有真实设备/EMS 可用，全部靠 Simulator 验证链路）
- 市场交易的完整规则（哪怕以后做，也只会先做一个"薄壳"）

**已知的局限 / 技术债（如实讲，这正是接下来"测试和找问题"阶段要重点关注的清单）：**

- Resource 里设计了一套"资产运行时缓存"，但目前只有读的代码、没有任何服务真正往里写数据，是一个"半成品"能力
- 服务与服务之间（比如 Dispatch 内部调用 Gateway）目前没有做身份校验，靠"都在同一个可信内网"这个假设，这是明确接受的阶段性取舍
- Alarm 的管理端查询接口还没接入统一网关，是直连的
- Gateway 这个名字容易让人误解成"所有对外流量的统一入口"，实际上它专精"外部系统适配"，管理端访问 Resource / Dispatch 从不经过它——文档措辞和实际定位有一点点错位，值得后续澄清
- 权限角色体系（管理员/操作员/查看者）是占位模型，真实业务角色还没定

## 13. 下一步：从"能跑"到"可信"（3 min）

这一节是这次分享真正的落脚点。

现在这套系统的状态是**"能跑"**——主链路都通了，服务都能起来。但作为负责人，我现在还不能完全确认它**"可信"**——有没有隐藏的 bug？边界条件处理得对不对？文档里写的和代码里实际做的是不是一致？

所以接下来我给自己定的任务，不是继续加新功能，而是：

1. **理清架构**——今天这次分享，以及配套的架构图，就是第一步产出，后续会持续补充和修正。
2. **系统性测试**——针对每个服务、每条业务闭环，设计正常路径和异常路径的测试用例。这里 Simulator 的**故障注入能力**（模拟设备离线、拒绝指令、上报延迟）是一个很好的抓手，可以低成本地把"异常场景"跑出来验证。
3. **找 bug、找不合理设计**——从代码细节反查，看是否和文档描述的行为一致，边界条件、并发场景、失败重试路径有没有考虑周全。
4. **能对着 PPT 讲清楚整个系统**——这次演讲稿是"从 0 到能讲"的起点；后续会再补一版"技术细节和亮点"专场，把值得展示的设计亮点（比如六边形架构、事件驱动、分级降级鉴权等）讲透。

**验收思路建议**：可以借助 Simulator 跑几条"黄金路径"（一切正常）和"故障路径"（人为注入异常），边跑边对照文档，检验"讲的和实际发生的是不是一回事"——这本身就是一种低成本、高信噪比的架构体检方式。

## 14. 结语 + Q&A 预案（2 min）

**结语：**

这套 VPP 中台，用 8 个各司其职的服务，把"认识资源、统一接入、记录状态、做出决策、执行控制、发现异常"这几件事串成了一条完整的闭环，并且用 Simulator 保证了在没有真实设备的情况下依然可以真实、可重复地验证整条链路。它现在的状态是"骨架搭好了，主链路跑通了"，接下来要做的是让它经得起测试、经得起细看。

**Q&A 预案：**

**Q1：为什么要拆这么多服务，不做一个大单体应用？**  
A：每个服务的职责边界很清楚（认识资源 / 协议转换 / 存数据 / 做决策 / 执行控制 / 告警），拆开之后改一个服务不容易牵连别的服务；服务之间用事件解耦，一个服务临时故障不会连锁拖垮全部。代价是需要多花心思在"服务之间怎么协作"上，这也是今天这次分享的重点。

**Q2：这套系统现在能直接上生产、接真实设备吗？**  
A：主链路已经打通，但目前控制指令的执行方还是 Simulator（虚拟设备），真实 EMS 的适配器还没有实现；服务间内部调用也还没有做零信任级别的身份校验。接真实设备之前，这些都需要先补上。

**Q3：如果要接入一个新的外部系统/新设备类型，要改哪里？**  
A：主要在 Gateway 里新增一个"出站适配器"（就像现在已经有的 Simulator 适配器一样），把这个新外部系统的协议翻译成平台内部统一的格式；Resource、Telemetry、Dispatch 这些服务基本不需要改动。这也印证了"协议差异只应该在 Gateway 这一层消化"的设计初衷。

**Q4：这套系统现在最脆弱的地方在哪？**  
A：几个已知点——服务间内部调用没有身份校验（依赖内网可信假设）；Resource 的运行时缓存是半成品；权限角色体系是占位；Optimization 目前只是简单规则，还没有真正的智能决策能力。这些也是接下来测试和加固的重点方向。

**Q5：数据都存在哪，安全吗？**  
A：每个服务有自己独立的数据库，互相不跨库查表；对外的所有入口都要经过统一网关做身份核验；控制类操作（Dispatch）的权限校验比一般的查询操作更严格，即使权限系统临时不可用，也是"宁可拒绝、不可放行"。

我的介绍就到这里，谢谢大家，欢迎提问。
