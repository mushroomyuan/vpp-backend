你对风险的判断是对的，但有一点看错了：计划没有把 `battery_storage_capabilities` 字段放进 `points`，而是准备建立独立的 CU 能力表。

不过当前计划仍然过于“电池中心化”，命名和持久化方案确实应该调整。

正确的分层应该是：

```text
CU
├── Capabilities：设备能做什么
└── Points：这些能力通过哪些指标实现
```

## Point 应保持完全设备无关

`points` 只描述指标绑定：

```text
point_id
cu_id
metric_id
external_address
access_mode
scale
offset
enabled
revision
```

它不应该出现：

- battery capacity
- PV rated power
- wind turbine parameters
- charger connector
- flexible load parameters

例如不同设备都可能绑定：

```text
electrical.active_power.v1
electrical.reactive_power.v1
electrical.active_power_setpoint.v1
```

储能额外拥有：

```text
energy_storage.state_of_charge.v1
```

所以原计划里的：

```text
battery.soc.v1
battery.active_power_setpoint.v1
battery.storage.v1
```

也偏设备类型化，更合理的是：

```text
energy_storage.state_of_charge.v1
electrical.active_power_setpoint.v1
energy.storage.v1
```

## Capability 应按“行为能力”建模

不要直接按设备种类设计：

```text
BatteryCapability
PVCapability
WindCapability
LoadCapability
```

因为同一个设备可能同时具备多种能力。比如储能既能充电、放电，也能调无功；充电桩既是用电设备，也可能支持 V2G。

应采用能力组合：

```text
energy.storage.v1
power.generation.v1
power.consumption.v1
load.flexibility.v1
reactive_power.control.v1
ev.charging.v1
ev.vehicle_to_grid.v1
```

例如：

```text
储能 CU
├── energy.storage.v1
├── power.generation.v1
├── power.consumption.v1
└── reactive_power.control.v1

光伏 CU
├── power.generation.v1
└── reactive_power.control.v1

柔性负荷 CU
├── power.consumption.v1
└── load.flexibility.v1

充电桩 CU
├── power.consumption.v1
├── ev.charging.v1
└── ev.vehicle_to_grid.v1（可选）
```

## 持久化建议也应修改

不建议为每类设备不断增加表：

```text
battery_storage_capabilities
pv_capabilities
wind_capabilities
charger_capabilities
...
```

更适合的是统一能力实例表：

```text
cu_capabilities
- id
- tenant_id
- cu_id
- capability_id
- schema_version
- spec JSONB
- enabled
- version
- created_at
- updated_at
```

其中 `spec` 不是任意 JSON。它必须由 `capability_id + schema_version` 对应的代码契约严格校验。

例如：

```json
{
  "capability_id": "energy.storage.v1",
  "schema_version": 1,
  "spec": {
    "usable_energy_kwh": 200,
    "max_charge_power_kw": 50,
    "max_discharge_power_kw": 50
  }
}
```

风机或光伏可以使用：

```json
{
  "capability_id": "power.generation.v1",
  "schema_version": 1,
  "spec": {
    "rated_power_kw": 500,
    "min_power_kw": 0,
    "max_ramp_kw_per_minute": 100
  }
}
```

这和之前反对自由文本 PointKey 并不冲突：

- `capability_id` 是代码定义的稳定契约。
- `schema_version` 决定严格的数据结构。
- `spec` 只保存设备实例参数。
- 数据库不能自行创建新的语义 ID。
- Resource 写入时必须反序列化为对应的强类型结构并校验。

## Decision 如何保持通用

不同 Policy 声明自己需要的能力和指标：

```text
SOCThresholdPolicy
需要：
- energy.storage.v1
- energy_storage.state_of_charge.v1 可读
- electrical.active_power_setpoint.v1 可写

PVLimitPolicy
需要：
- power.generation.v1
- electrical.active_power.v1 可读
- electrical.active_power_setpoint.v1 可写

FlexibleLoadPolicy
需要：
- load.flexibility.v1
- electrical.active_power.v1 可读
- 相应控制指标可写
```

因此 Asset/Site 可以包含混合设备。`ResolveScope` 根据 Policy 的需求选择符合条件的 CU，而不是假设所有 CU 都是电池。

结论：

- `points` 中不会加入任何电池字段。
- 原计划独立的 `battery_storage_capabilities` 表也不够通用，应删除。
- 改成统一的 `cu_capabilities`，通过版本化、强校验的 capability spec 支持多种设备。
- canonical metric 也应尽量使用技术中立的物理语义，而不是统一加 `battery` 前缀。
