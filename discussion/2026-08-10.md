## 需要你留意的几个点（按严重程度）



### 1. 【重要，但已知且当前无害】dispatch/telemetry 的 gRPC PEP 目前没有真正可信的接入点

`internal/platform/middleware/grpcauth/auth.go` 要求调用方在 gRPC metadata 里带 `x-userinfo`，但 `AUTHZ_CENTRALIZATION_PLAN.md` 自己写了："生产级 APISIX gRPC 路由留待后续"——也就是说，目前没有任何组件在网络边界上验证一个真正的 Bearer token、再把可信的 `x-userinfo` 注入进去。HTTP 这条链路上 APISIX 的 `openid-connect` 插件承担了这个角色，但 gRPC`:5006` dispatch`:5003` telemetry）目前谁都可以直接连上去，在 metadata 里自己塞一个 `x-userinfo: {"roles":[{"name":"admin"}], "owner":"default"}`。

**现状是安全的**，因为我确认了 `config/dispatch.yamlconfig/telemetry.yaml` 里 `trust-proxy-headers` 默认都是 `false`——也就是说这套鉴权目前根本没打开，只是搭好了骨架和测试。真正的风险点是：**未来如果为了"验收 C10a/C10c 已完成"而在非隔离网络环境把这个开关打成** `true`**，会造成一种"看起来有鉴权、实际上任何能连上端口的人都能自签 admin 身份"的假安全感**——比完全不鉴权更危险，因为它会让人误以为已经防护到位。

建议：在打开这两个开关之前，要么先把 gRPC 网关落地（APISIX gRPC 代理或独立的 mTLS/token 校验层），要么至少用防火墙/Docker network 把 `:5006:5003` 收紧到只有可信调用方能触达，并在文档里明确写清楚"这个开关的安全性依赖于网络隔离，不是自证的"。这个我建议放进接下来讨论的 K8s 阶段一起解决（ClusterIP 天然收紧暴露面）。

### 2. 【建议做一次实测,而非理论问题】APISIX 是否会覆盖客户端伪造的 `X-Userinfo`

`resource-proxy` 路由的 `openid-connect` 插件配了 `set_userinfo_header: true`。理论上 APISIX/OpenResty 的 `ngx.req.set_header` 是覆盖语义不是追加，客户端自己发的 `X-Userinfo` 应该会被合法 token 解出来的值覆盖掉——但这是我基于对 nginx/OpenResty 常见行为的推断，不是我在你的环境里实测验证过的。

建议你自己做一次实验：直接对 `:9080/resource/*` 发一个请求，同时带上**合法 Bearer token** 和一个**手工伪造的** `X-Userinfo: {"owner":"other-tenant","roles":[{"name":"admin"}]}` header，确认 Resource 收到的是 APISIX 覆盖后的值，而不是你伪造的那个。这个实验成本很低（一条 curl），但能把"我认为安全"变成"我验证过安全"，面试时这也是一个很好的"我如何验证边界条件"的故事。

### 3. 【已知且已被你自己标注,不是新发现】直连端口目前不受 APISIX 保护

`resource:8082dispatch:5006` 等端口目前都监听在宿主机上`trust-proxy-headers:false` 时直连是完全绕过鉴权的（这是为了本地调试故意设计的）。你在 `docs/CASDOOR.md` 里已经写了"K8s 后 Resource 仅 ClusterIP 时,伪造面自然缩小"，说明你已经意识到这是个阶段性权衡，不是遗漏。当前单机 docker-compose 环境下问题不大，但值得在 K8s 阶段作为一个明确的验收项："业务端口不再监听在 host 网络，只能通过 APISIX/Ingress 到达"。

### 4. 【设计取舍,建议能讲清楚而不是现在就改】内部服务间 gRPC 完全没有鉴权/mTLS

`dispatch → gateway`（ExecuteCommand）`gateway → telemetry`（IngestTelemetry）这些内部调用完全依赖"同一个内网可信"这个假设，没有 mTLS 也没有服务间 token。这是绝大多数单体转微服务早期项目的正常状态（南北向先做，东西向后做），我不建议现在补——但建议你能主动讲出这是"perimeter security 模型，尚未做 zero-trust 的东西向加固"，这本身就是一个成熟的架构判断，比"没注意到"要好得多。真要做的话，自然的落点是以后引入 service mesh（Istio/Linkerd）或者手动 mTLS，那是 K8s 之后的事。

### 5. 【小,记录即可】角色模型目前是占位的三元角色

`admin/operator/viewer` 这套在文档里反复被标注为"现状占位角色，不代表最终业务模型"——这个态度是对的，说明你没有过早把不成熟的业务角色设计固化进 Casbin 策略里。等真正的业务角色模型（比如按站点/资产分权限）明确后再细化 Casdoor 里的 Permission 就行，架构本身`PermissionChecker` 接口 + Casbin Model）不需要因此改动。

---

**小结**：没有发现会阻塞你继续往下走的架构问题。第 1 点建议在打开 dispatch/telemetry 的 `trust-proxy-headers` 开关前处理（或者干脆记录成一个"已知限制，待 K8s 阶段解决"），第 2 点建议花 5 分钟实测一下。这两点处理完，这套授权体系在面试里会是一个非常扎实的加分项——大概率比大多数同级别候选人做得更深。

## 关于 gRPC 认证风险的详细展开

先把攻击链具体化,这样你能自己判断这个风险的严重程度。

**攻击场景（假设条件成立时）：**

1. 前提条件 A`config/dispatch.yaml` 的 `trust-proxy-headers` 被改成 `true`（目前默认 `false`，这个前提当前不成立）
2. 前提条件 B：某个攻击者（内网被入侵的机器、配置错误导致暴露到公网的端口、或者以后 K8s 里同 namespace 但不该有权限的另一个 Pod）能够建立到 `:5006` 的 TCP 连接
3. 如果 A 和 B 同时成立，攻击者可以直接用 `grpcurl` 或几行 Go 代码，带上自己伪造的 metadata：

```

x-userinfo: eyJvd25lciI6ImRlZmF1bHQiLCJuYW1lIjoiYXR0YWNrZXIiLCJyb2xlcyI6W3sibmFtZSI6ImFkbWluIn1dfQ==

```

（即 `{"owner":"default","name":"attacker","roles":[{"name":"admin"}]}` 的 base64）

1. `internal/platform/middleware/grpcauth/auth.go` 里的拦截器不会去验证这段 metadata 是不是从一个经 Casdoor 签名、经 JWKS 验签过的真实 JWT 里解析出来的——它只是**信任**调用方声明的身份。HTTP 路径上这个信任是有依据的（APISIX 的 `openid-connect` 插件先验证了 JWT 签名，验证通过才生成 `X-Userinfo`，客户端自己伪造的会被覆盖）；gRPC 路径上没有等价的"先验证签名再生成身份"的环节。
2. 拦截器会认为这是一个合法的 admin，直接放行 `SubmitTask` / `CancelTask` —— 这条链路最终会驱动物理设备动作。

**为什么现在不用紧张：** 前提条件 A 目前不成立（默认 `false`，代码在这个分支下甚至不解析 `x-userinfo`，直接 `return handler(ctx, req)`）。真正的风险窗口是"未来某次为了验收 C10a 而把开关打开，但没有同步做网络隔离"这个操作失误，而不是当前代码状态有漏洞。

**三个处理层级，成本递增：**

| 方案 | 成本 | 效果 |

|---|---|---|

| **文档/流程护栏**（现在就能做） | 几乎为零 | 在 `AUTHZ_RUNBOOK.md` 加一条"启用 `trust-proxy-headers` 前置检查清单"：必须先确认网络层已隔离该端口（防火墙规则/K8s NetworkPolicy），否则等于自证空转的假安全感。可以再加一行代码`TrustProxyHeaders=true` 但从未见过一次成功 sync 时，除了走冷启动安全网，额外打一条更醒目的启动期 WARN 日志 |

| **APISIX 挡在 gRPC 前面** | 中等，需要先验证可行性 | APISIX 对 gRPC 流量的插件支持是分插件的，不是所有插件都对 gRPC-over-HTTP/2 生效，需要先花小半天验证 `openid-connect` 插件能不能用在 gRPC route 上；如果可以，就能复用现有 Casdoor 体系，不用等 K8s |

| **Service Mesh mTLS** | 最高，但是"顺便"解决的 | 等 K8s + Istio/Linkerd 落地后，东西向和南北向的身份问题一起解决，不需要单独为 gRPC 造轮子 |

我的建议是：**现在先做第一档（零成本护栏），把这个风险从"未知的坑"变成"已知且有文档护栏的坑"；是否要提前做第二档，取决于你打算多久之后上 K8s**——如果 K8s 计划在 1-2 个月内，不值得单独搭一套 APISIX gRPC 方案再推倒重来；如果 K8s 遥遥无期，那提前把这层补上更划算。这个可以等 K8s 排期定了再决定，不影响你现在做别的事。

## Phase A 剩余项的依赖关系

我检查了一下，目前项目里**没有任何 Dockerfile、没有 CI 配置、没有 K8s manifest**—`make run-all` 现在是直接编译 Go 二进制在 host 上跑，这个事实会影响排期，因为它是 CI 的 docker-build 步骤和 K8s 部署的共同前置。

依赖关系图大致是这样：

```

CI/CD (build+vet+现有单测) ──┐

                              ├──▶ CI 加 docker build/push ──▶ K8s 基础部署（顺带解决端口暴露问题）

集成测试（补进 CI）───────────┘

Alarm 服务 ───────────────────── 独立，无依赖，随时可插入

CancelTask ───────────────────── 独立，无依赖，随时可插入

```

具体来说：

- **CI/CD 值得最早做**，即使集成测试还没写。先跑 `build + vet + 现有单测`，价值是"从今天起，之后每一次改动都有自动化验证"，越早接入复利效应越强；集成测试写好后再作为一步加进同一条流水线，不是必须等集成测试完成才能上 CI。
- **集成测试**本身和 CI 没有强制的先后关系，可以先写完再接进 CI，也可以边写边加，看你自己的节奏。
- **K8s 基础部署**依赖"服务能被容器化"这个前置（目前完全没有 Dockerfile），而容器化这一步本身适合放在 CI 里做`docker build` 步骤），所以 K8s 排在 CI 之后是有实际依赖的，不只是"重要性"排序。K8s 落地后 ClusterIP 也顺带处理了前面提到的端口暴露问题。
- **Alarm 服务和** `CancelTask` 两者互相独立，也不依赖上面任何一项，可以在等 CI/K8s 推进的间隙见缝插针地做，谁先谁后都可以。

**我建议的顺序**：CI/CD（先跑起来）→ 集成测试（补进 CI）→ Alarm / CancelTask（穿插进行，顺序随意）→ K8s 基础部署（此时才有意义，因为已经有可信的镜像构建流程）。这个顺序你觉得合理的话，我把它写进 [ROADMAP.md](http://ROADMAP.md)；如果你有不同的优先级判断（比如更想先看到 Alarm 服务跑起来产生"新服务"的成就感，而不是先啃 CI 这种基建），也可以调整，两者没有对错，纯粹是你自己时间预算和心理节奏的问题。
