## 一、背景：Phase A 已收口，体检结论

对照 `ROADMAP.md`、`AUTHN_AUTHZ.md`、`architecture.md`、六个服务的 `OVERVIEW.md`，2026-07 架构复审"无阻塞性问题"的结论今天依然成立。7 个服务（resource/telemetry/gateway/dispatch/simulator/alarm + platform）跑通主链路，Phase A 的认证鉴权/CI/CD/集成测试/K8s 基础部署/Alarm/CancelTask 全部收口。

本轮体检在已知限制表之外，额外识别出几个建议在做 Phase B（Forecast/Optimization）**之前**想清楚的点：

| # | 风险点 | 说明 |
|---|---|---|
| 1 | 单实例 Postgres/Kafka/Redis 是全平台 SPOF，不只是 Casdoor 的问题 | 现在挂了只影响开发联调；Optimization 自动决策上线后，挂了会直接打断闭环控制 |
| 2 | dispatch 的 `CancelTask` 对 `Sending` 状态命令只是"名义取消"（Gateway 没有撤回出站能力） | 现在 EMS 是 log-only 误操作代价低；Optimization 自动触发后，误判后果从"人工不好收场"升级为"算法不好收场" |
| 3 | 内部服务间调用完全没有限流/熔断（`microservices_framework.md` 早就指出但没做） | Optimization 会是第一个"定时轮询读 telemetry + 高频调 dispatch"的角色，没有限流的话一次规则误触发可能对下游造成突发压力 |
| 4 | Optimization → Dispatch 的身份路径此前没有先例 | **已决定**：走内部直连（不经 APISIX/PEP），和 gateway→telemetry 的信任模型一致。代价：审计上"人下发"和"算法下发"混在一起，需要在 `SubmitTask` 请求里带 `Source`/`initiator` 字段做区分，现在没做 |
| 5 | 决策周期必须显式大于遥测采集周期（Simulator 默认 30s） | 否则会对同一份 stale 数据反复决策，出现震荡 |
| 6 | gateway 定位问题（Roadmap 已列，未展开怎么判断） | **建议**：用 Optimization 的实际调用方式反过来验证——如果 Optimization 直接裸连 resource/telemetry/dispatch（像 simulator 现在对 resource 的只读直连一样），就印证了"gateway 只是 EMS 适配器"这个定位，不需要现在为了这个决策去动 gateway |

## 二、业务全景：当前 7 个服务在 VPP 业务链条里的位置

用户当前的困惑：不清楚现有工作和"需求响应/调峰调频/现货市场/辅助服务市场/中长期市场/电价预测"这些真实 VPP 业务的关系,担心是否走偏。

结论：**没有走偏，只是还没到业务化阶段，这是正确的顺序。**

```
市场/收益层（Phase D「Market」，几乎没做）      —— 出价/清算/结算/合规申报
决策/优化层（Phase B「Optimization」，未做）    —— 把信号+状态+预测变成"要不要动、动多少"
预测层（Phase B「Forecast」，未做）             —— 给优化层/市场层提供"接下来会怎样"
接入/控制执行层（现有 7 个服务，已完成）         —— 感知资产状态 + 可靠下发控制指令 + 异常兜底
```

业务术语和架构分层的对应关系：

| 业务概念 | 主要输入 | 落到哪层 |
|---|---|---|
| 调峰调频 | 内部资产状态 + 短期资产出力预测，**几乎不需要外部数据** | Optimization + Dispatch，纯内部闭环 |
| 需求响应 | 外部邀约信号 + 各资产可调容量预测 | Market（接邀约）→ Optimization（分摊）→ Dispatch（执行） |
| 电力现货市场 | **电价预测**（外部数据）+ 资产约束 | Forecast（电价，需要外部数据）→ Optimization → Market → Dispatch |
| 辅助服务市场 | 类似现货，计价规则不同 | 同上 |
| 中长期市场 | 长周期价格趋势 | 更偏离线分析/人工决策，优先级最低 |

**关键区分（决定了 Forecast 的范围）**：调峰调频这类"纯内部"策略只需要资产状态 + 资产出力预测，可以现在就做；现货/辅助服务/需求响应这类"参与外部市场"的策略才需要电价预测/邀约这类外部信息。

**Forecast 的范围决策**：资产出力/负荷预测（只读 telemetry，服务 Optimization）和电价/天气/政策这类"辅助交易决策"预测，**是两种完全不同的东西**（输入、消费者、可靠性要求都不同），不应该合并到一个服务里。当前 Forecast v1 **只做资产出力预测**；"辅助交易决策"明确标记为 Phase D 之后、依赖外部数据接入、现在只占位不写代码。

## 三、Forecast v1 / Optimization v1 已达成的设计共识

### 3.1 身份/鉴权
Optimization → Dispatch 走**内部直连**，不经 APISIX/PEP（和现有 gateway→telemetry 信任模型一致，架构一致性最高）。遗留 TODO：`SubmitTask` 需要带来源标记以便审计区分"人下发"/"算法下发"，现在没有这个字段。

### 3.2 Forecast 存储

**原结论（有盲点，已修正）：** 最初讨论时说"只存 Redis，不建 Postgres 库"，理由是"短生命周期派生数据，重启可重算"——这个理由只考虑了 Optimization 这一个消费者（它只关心"当前最新一次预测"）。

**盲点**：如果前端要展示"预测曲线 vs 实际曲线"这种图表（对算法效果建立信任、评估准确率的常见需求），或者以后需求响应基线要留痕给结算/合规稽核用，**历史预测值必须持久化**——Redis 每个周期覆盖写入，旧的预测批次会直接丢失，且同一个未来时间点会被多次不同批次预测过（比如"提前 4 小时的预测"和"提前 1 小时的预测"精度通常不同，只有分别保留才能做这种分析），Redis 的"覆盖式"存储结构从设计上就不支持这个需求。

**修正后的结论——分两层，参考 Telemetry 自己"权威存储 + 热点缓存"的既有模式**：

| 层 | 存储 | 服务谁 | 特点 |
|---|---|---|---|
| 最新值（热点） | Redis，TTL | Optimization | 高频读，只要最新一条，可重算，丢了不心疼 |
| 历史批次（权威） | 新建一张 Postgres 表（不需要 TimescaleDB 超表，量级远小于原始遥测） | 前端预测曲线图、算法效果评估（MAPE/RMSE 等）、未来需求响应基线留痕 | 每次批算是一条"预测运行记录"，记录 `生成时间` + `预测的目标时刻` + `预测值` + `算法版本`，不覆盖 |

建议的历史表大致形状（讨论阶段草案，非最终字段）：

```
forecast_history:
  id, tenant_id, cu_code, metric_name,
  generated_at        -- 这次预测是什么时候算出来的
  target_timestamp    -- 预测的是哪个未来时刻
  predicted_value
  algorithm_version   -- 对应 Predictor 的哪个实现/版本
```

前端画"预测 vs 实际"对比图时：按 `target_timestamp` 拉 `forecast_history`，同时按同一时间窗查 Telemetry 的 `QueryAggregation` 拿实际值，两条线一起画。

**补充讨论：`forecast_history` 该用普通表还是 TimescaleDB 超表？—— 普通表就够，不需要上 TSDB。**

预测历史数据技术上是时序数据，但它有一个和原始遥测不一样的特殊形态：**双时间轴（bi-temporal）**——`generated_at`（这次预测是什么时候算的）+ `target_timestamp`（预测的是哪个未来时刻），同一个 `target_timestamp` 会被不同 `generated_at` 反复预测多次（这在数据库领域是双时态数据的标准场景，类似金融"某时点看到的价格 vs 事后修正价格"）。这和大部分 TSDB 默认假设的"一根时间轴、一个序列一个值"模型不完全匹配。

对比 TSDB（TimescaleDB 现在给 Telemetry 用）真正为之优化的三件事，预测历史数据几乎都对不上：

| 特征 | 原始遥测（TSDB 目标场景） | 预测历史数据 |
|---|---|---|
| 写入频率 | 高（每 CU 每 tick，Telemetry 现在 30s 一次） | 低（每次批算一次，如 15~60 分钟一次） |
| 时间轴数量 | 1 根 | 2 根（`generated_at` + `target_timestamp`） |
| 是否需要连续聚合降采样 | 需要（原始密度高，Telemetry 已经在用 15 分钟连续聚合视图） | 不需要（预测本来就是已经降采样过的衍生产物，没有比它更细的原始数据要压缩） |
| 是否需要和其他关系型数据 join | 较少 | 较多（`algorithm_version` 等模型/规则版本元数据，关系型 join 更自然） |

**业内做法**：低频批量预测结果（负荷预测、需求响应基线这类）更常见的做法是放普通关系型数据库或数据仓库，当成"有版本、有血缘的模型输出产物"管理；只有推理频率已经逼近原始采样频率的超大规模场景（比如给几十万序列每分钟推理一次，直接叠加进监控大盘），才会考虑 InfluxDB/Prometheus remote-write 这类方案。

**结论**：`forecast_history` 用普通 Postgres 表即可，`target_timestamp` 上建索引支持"查某个时间窗口的预测"，不需要 TimescaleDB 超表。如果以后预测频率暴涨到接近遥测频率（现实中不太可能，预测没必要比原始数据更新更快），可以直接复用 Telemetry 已经在跑的 TimescaleDB 实例加一张新超表，不需要引入新存储组件。

### 3.3 数据输入——两者都不依赖 Resource 的 Runtime 缓存，直连 Telemetry

调查发现 Resource 的 `AssetRuntime`/`CURuntime`/`PointRuntime` 三级 Redis 缓存**只有读路径，没有任何服务写入**（`resource_service.proto` 没有暴露写 RPC，gateway/telemetry 代码里也没有调用）。这是早期"冷热分离"设计遗留，Telemetry 后来自建了一套独立且真正在用的 `Snapshot`（Redis db=1，按 CUCode 存 `map[MetricName]float64`），Resource 这套变成悬空能力。已把完整调查结论写入 `architecture.md` §3.3.1 和 `internal/resource/domain/resource_v2.md`。

**易搞反的结论，第二轮讨论后修正过一次**：
- 这层缓存（如果做）的驱动力是**前端**——资产详情/列表页想一次性拿到"配置+当前状态"，容忍 15~30s 滞后。
- **Optimization 不应该依赖它**，不管它做不做都应该直连 Telemetry——决策对新鲜度的要求比前端高，缓存的轮询间隔对它是实质性延迟成本。
- 如果以后 Optimization 想复用 Resource 已经算好的"多 CU 聚合成 Asset 级判断"的业务规则，可以给 `GetAssetRuntime` 加一个按需强制刷新的变体，但 v1 不需要。
- 是否要实现这层缓存（`RuntimeSyncWorker`，Resource 内新增单 goroutine 定时轮询 Telemetry 的 `GetFleetSnapshot`/`QueryAggregation`，pull 而非 push），完全取决于前端体验需不需要，跟 Optimization 设计无关。

### 3.4 决策粒度：`Target` / `Allocate` / `ControlCommand` 三段式

**问题起点**：用户发现"拉指标→检测→生成任务给 dispatch"这条自动化路径，和"电网/市场下发已分解任务→优化→执行"这条路径，看起来一个是"输入指标输出任务"，一个是"输入任务输出任务"，感觉架构别扭。

**解法**：这是两种粒度的"任务"被同一个词混用导致的错觉，拆开后不矛盾：

```
Target（抽象调节目标，不管来自哪条路径）──Allocate（分配算法）──▶ []CommandSpec（喂给 dispatch.SubmitTask）
```

和 Dispatch 自己的 `Task → Action → Command` 三级分解是同构的、更上一层的复用，不是新发明的范式。

**`Target` 是一个 oneof，两条路径填不同的分支，粒度天然不同**：

```go
type Target struct {
    TenantID string
    Source   string // "internal_rule" | "external_dr" | "external_market"

    Points    []PointTarget    // 规则触发路径：细粒度，逐 CU 逐 Point，已经算好具体值，Allocate 直接透传
    Aggregate *AggregateTarget // 外部下发路径：粗粒度，一批资源 + 一个总量指标，Allocate 需要做分摊
}

type PointTarget struct {
    CUCode   string
    PointKey string
    Value    CommandValue
}

type AggregateTarget struct {
    Scope      []string   // 一组 CUCode 或 AssetID
    Metric     string     // 如 "active_power_kw"
    DeltaValue float64    // 目标变化量，正负表示方向
    Window     TimeWindow
}
```

`Allocate(Target) -> []CommandSpec`：`Points` 分支直接映射；`Aggregate` 分支要先查 `Scope` 内每个资源的当前可调容量（直连 Telemetry）,再按比例分摊（v1 可以是"按 `MaxDischargePowerKW` 占比线性分摊"），换算成每个 CU 具体的 `PointKey`+`Value`。两条分支输出统一后，由外层打包成 `ActionSpec`（多 CU 同时调节通常 `ExecutionPolicy=parallel`）→ `SubmitTaskRequest`。Dispatch 侧完全感知不到上游是规则触发还是外部下发。

**顺带发现，未深挖**：`AggregateTarget.DeltaValue` 在真实需求响应业务里通常是相对"基线负荷"算出来的，"基线"本身也是一个预测问题——Forecast 服务除了服务 Optimization 的阈值规则，未来在需求响应场景下还有第二个用途："算基线"。现在不需要处理，先记录（§3.6 展开了一版构想）。

### 3.5 `Target` 用 interface，不用 `CommandValue` 那种扁平 struct + 可选字段

**问题**：`PointTarget`/`AggregateTarget` 是互斥载荷，为什么要塞进同一个 `Target{Points, Aggregate}` struct，而不是用接口抽象？

**结论：应该用 interface。** 项目里 `dispatch.CommandValue`（`internal/dispatch/domain/model/command_value.go`）是同类问题的先例，选的是"扁平 struct + 可选字段 + 运行时 `Validate()`"，但它的适用条件是**分支少（4个）、分支内容是简单标量、以后基本不会再增加分支**。`Target` 不满足这些条件：两个分支字段集合几乎不重叠（`PointTarget` 要 `CUCode`/`PointKey`，`AggregateTarget` 要 `Scope`/`Metric`/`Window`），且未来大概率会长出第三个分支（多级分解如果做了，可能需要 `DelegatedTarget`；基线相关也可能衍生出带调度性质的变体）。

用 interface 写法：

```go
type Target interface {
	TenantID() string
	Source() string
}

type PointTarget struct {
	Tenant, Src      string
	CUCode, PointKey string
	Value            CommandValue
}
func (t PointTarget) TenantID() string { return t.Tenant }
func (t PointTarget) Source() string   { return t.Src }

type AggregateTarget struct {
	Tenant, Src string
	Scope       []string
	Metric      string
	DeltaValue  float64
	Window      TimeWindow
}
func (t AggregateTarget) TenantID() string { return t.Tenant }
func (t AggregateTarget) Source() string   { return t.Src }

func Allocate(ctx context.Context, t Target) ([]CommandSpec, error) {
	switch v := t.(type) {
	case PointTarget:
		return pointToCommands(v), nil
	case AggregateTarget:
		return splitByCapacity(ctx, v)
	default:
		return nil, fmt.Errorf("optimization: unsupported target type %T", t)
	}
}
```

**为什么不选 struct（反驳"struct 更好序列化"这个直觉）**：查了 `CommandValue` 落库的代码（`internal/dispatch/adapter/outbound/postgres/converter.go`），即便它选了扁平 struct，落库时依然得手写一个带 `Kind` 标签的 DTO 做 marshal/unmarshal——**跨边界（落库/gRPC）时不管内部选 struct 还是 interface，都得写一次判别式转换代码，工作量跑不掉**，所以"struct 更适合序列化"不成立，不是决定因素。

**真正的取舍**：
- interface 的好处——不可能构造出"两个字段都设了"或"都没设"的非法中间态（struct 得靠 `Validate()` 运行时兜底）；新增分支是纯加法，不用改已有类型定义。
- 需要诚实说明的局限——Go 的 `type switch` **不提供编译期穷尽性检查**（不像 Rust/Swift 的 `match` 会强制处理所有分支），新增分支时如果漏改某个 `switch`，编译器不会报错，只会走到 `default` 分支报运行时错误。这一点上 interface 并不比 struct 更安全，两者都得靠代码审查/测试兜底。

### 3.6 基线预测（需求响应场景）的实现构想——粗略草案，非最终设计

**核心洞察：基线预测可以复用 Forecast 已经设计好的可插拔 `Predictor` 接口，不需要另建体系。** "预测接下来会怎样"（服务 Optimization）和"预测如果没有响应事件、原本会是多少"（服务需求响应结算）本质上是同一个接口的两种实现/两种调用场景，只是训练数据的选取规则不同。

粗略构想：

```
BaselinePredictor（Predictor 接口的一个实现）：
  输入：TenantID, Scope（CU/Asset 列表）, EventWindow（需要响应的时间段）
  算法（v1 可以用行业常见的朴素方法，如 CAISO/PJM 的"历史同期均值法"）：
    1. 取过去 N 天（如 10 天）里，非事件日、同一时段的历史 QueryAggregation(AVG)
    2. 取平均或中位数，作为"如果不响应，本来会是多少"的基线
  输出：和其他 Predictor 一样的 PredictedSeries 结构，Source 标记为 "baseline"
```

**一个诚实的依赖说明，不要过度承诺**：上面第 1 步"排除非事件日"依赖一份"历史上哪些日子发生过需求响应事件"的事件日历——这份数据现在系统里完全没有（属于 Market 服务的范畴：谁参与了需求响应、哪天发生了事件）。也就是说，`BaselinePredictor` 现在只能**先把接口和粗略算法框架搭起来**，真正跑出有意义的基线值，要等 Market 服务把"历史事件记录"这个数据源做出来之后才行——这是一个先后依赖关系，不是 Forecast 自己能闭环解决的。

## 四、多级任务分解（聚合商→代理用户→CU）——已讨论但明确推迟

**背景**：用户提出真实需求响应场景里，电网下发任务给聚合商后，聚合商要按代理用户分解，代理用户再往下分解到 CU，问这个分解工作是否归 Optimization。

**调查结论**：当前系统完全没有建模"多级组织/代理关系"——`Asset.OwnerType`（`self`/`third_party`/`customer`）只是一个描述性标签，`TenantID` 全系统扁平单层，没有"容量合约"实体，没有"代理商/账户"层级节点。

**用户已确认**："代理用户"目前更倾向于是内部业务分组，不是拥有独立调度系统的外部主体（现实中国内聚合商业务大部分也是这个形态：终端用户没有自己的调度软件）。

**结论/推迟原因**：
1. 多级分解依赖"多级组织/合约关系"数据模型，这个模型现在完全不存在，是一块独立的、更大的建模工作。
2. 即使不考虑跨层级分解，**同一层级内多 CU 间的分摊**（`AggregateTarget` 那条路径的 `Allocate` 分摊算法）已经能覆盖"同层级分配"的需求，不需要等多级组织模型就能做。
3. 如果以后要支持跨层级递归分解，`Target → Allocate` 这套结构不需要推倒重来——`Allocate` 判断"子对象是否还能再往下分"时，递归调用同一套逻辑即可；如果代理用户以后真的变成外部系统，"递归调用"这一步换成"通过北向接口把子任务扔给对方"，其余不用动。

**当前状态**：**暂不纳入 Phase B 范围**，Optimization v1 按单层假设做（`AggregateTarget.Scope` 直接是一批 CU/Asset，不含多级代理关系）。多级分解作为一个已经想清楚方向、但明确推迟的后续方向记录在此，不落入 ROADMAP 正式条目（用户选择"先讨论，不着急做计划"）。
