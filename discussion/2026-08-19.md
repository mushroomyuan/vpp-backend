
**结论：先收口 Phase A，做告警中心（可顺手补 `CancelTask`），不要立刻开下一档 K8s 迁移，也不要跳去预测/优化/审计。**

一阶段 K8s 已经按当时划的边界做完了。接下来再迁 APISIX / Casdoor / 有状态组件，是另一类工作，不是「同一条迁移的第二周」。新服务里，告警是唯一「事件已经在产、文档写了没做、能立刻挂到现有 kind 上」的项。

## 一阶段到底完成了什么

对照 `ROADMAP.md` 和 `discussion/K8s 迁移.md`，这一轮的目标本来就是：

> 5 个无状态业务服务进 kind：Deployment + ClusterIP + 探针 + env 覆盖；APISIX / Casdoor / Postgres / Kafka 留在 Compose。

这些已经落地：GHCR 镜像、`deploy/k8s/base`、Service DNS 互调、旧 host `:808x/:500x` 收口、Consul 运行时摘掉、`make k8s-exposure-check`。

**还没做、但当时就明确「不是这一轮」的：**

| 下一档 | 本质 | 为什么现在不该接着啃 |
|---|---|---|
| APISIX + etcd 进集群 | 边缘产品，要先选「传统 Admin API」还是 Ingress Controller | 换的是网关用法，不是再写一份 Deployment |
| Casdoor 进集群 | 和 APISIX 绑在 OIDC `origin`/JWKS 上，应成对移动 | 拆开迁会在 kind/compose 之间再拆一条身份链路 |
| Postgres / Kafka / Redis | StatefulSet / Operator / PVC | 单独就能开一个项目；现在没有数据丢失风险要解 |
| HPA、多节点、NetworkPolicy | 压测和东西向加固 | ROADMAP 把压测放在 Phase C；`resource`/`dispatch` 还不能随便 `replicas: 2`（Kafka 消费组语义未按多副本设计） |

混合拓扑是刻意过渡：业务藏 ClusterIP，外面只打 APISIX，Compose 经 NodePort hairpin 进来。`docs/K8S_DEPLOYMENT.md` 写得很清楚——真正「只有 APISIX 能打到 Pod」要等 APISIX 进集群后再删 `extraPortMappings`。host 上 `:30082` 仍能绕过插件，这是已知残余，不是一阶段没做完。

## 为什么不要「接着迁 K8s」

继续迁的边际收益会掉下来。

1. **学习目标已经换了。** 一阶段练的是 Deployment / Service / 探针 / 滚动发布 / 配置覆盖。下一档是边缘、etcd 状态、OIDC 契约、有状态存储。对简历是加分，但和「再做一个业务服务」比，每小时信号密度更低——你们 7 月已经把 CI + 鉴权 + kind 排在前面，正是因为当时基建缺口更大；现在基建已经能跑。
2. **平台最好立刻被用起来。** 刚有 kind，最有说服力的下一步是：再加一个服务，走同一套 manifests / CI 镜像 / Service DNS。这证明集群不是演示用 YAML，而是可扩展的运行时。
3. **APISIX 进集群解的是旁路，不是业务能力。** 值得做，但是一次独立的、边界清楚的切片，不该占满下一阶段。

## 为什么下一刀是告警，而不是预测或审计

`architecture.md` 里四条 Kafka topic 的消费面已经不对称：

| Topic | 生产者 | 现有消费者 | 缺口 |
|---|---|---|---|
| `vpp.resource.events` | resource | gateway lifecycle | 无 |
| `vpp.command.events` | gateway | dispatch 状态机 | 无 |
| `vpp.dispatch.events` | dispatch | **没有** | 告警反复写在文档里 |
| `vpp.soe.events` | telemetry | **没有任何服务** | 离散量变位无人处理 |

告警正好吃后面两条。工作量是「新消费者 + 落库/查询 + 可选通知」，不改现有生产者，风险低。7 月就把这项标成**投入产出比最高**的新服务；ROADMAP Phase A 现在只剩它和 `CancelTask`。

另外三个方向现在都不划算：

**预测 / 优化（Phase B）**  
这才是「VPP 变聪明」的一环，但依赖你发明一套（哪怕很 naive 的）策略，还要读 telemetry、调 `SubmitTask`。`architecture.md` 也说：编排层（改 gateway 还是新建 BFF）要等有真实组合调用再判断。现在跳过去，会同时引入新领域模型、新同步调用、以及「gateway 到底是不是业务网关」这场还太早的讨论。

**审计中心（Phase C）**  
和告警都是「纯新增 Kafka 消费者」，但目标不同：告警是规则 + 当前状态（task failed、SOE 变位）；审计是全量落库 + 按 CommandID/TaskID 查生命周期。现在两个一起做，很容易做成两个几乎一样的事件仓库。正确顺序是先告警把消费模式跑通，审计以后复用同一套 envelope / consumer 骨架，只换「全量归档 + 查询」。

**再开一档 K8s**  
不增加任何业务闭环。NodePort 旁路可以记在「已知限制」里，等告警上集群之后，用一次薄切片处理 APISIX 进集群。

## 建议的下一阶段（仍叫 Phase A 收口，大约 1～2 个迭代）

**1. 告警服务（主线）**

范围收紧，避免做成「第二个审计」：

- 消费 `vpp.dispatch.events`（task failed / 超时）和 `vpp.soe.events`（离散量变位）
- 规则先写死或 YAML：例如 task failed → critical；SOE 指定测点变位 → warning
- Postgres 存告警记录 + 列表/详情查询（HTTP 或 gRPC 均可，北向仍走现有 APISIX Path C）
- 通知第一版打日志或 webhook stub 即可，不要上邮件/短信
- 放在 `internal/alarm/`，继续用手写 `platform` 风格（7 月建议：框架实验留给 Forecast，不要第一次新服务就上 Kratos）
- 直接加 kind Deployment，Kafka 仍指 `host.docker.internal`——这是对一阶段平台的验收

刻意不做：全量事件归档、复杂抑制/收敛、按站点的业务角色、多副本消费者。

**2. `CancelTask`（插空，很小）**

proto 和 PEP catalog 都有了，handler 仍是 `Unimplemented`。它补的是控制面闭环，告警也能多一条「任务被取消」的事件。不必和告警绑死，谁先做都可以。

**3. K8s 只做「用起来」，不做「迁下去」**

告警的 manifests 复用现有 kustomize。不要顺手把 APISIX/Casdoor/Postgres 拖进来。`resource`/`dispatch`/`gateway` 继续 `replicas: 1`。

## 再往后怎么排

告警能在 kind 上跑通之后，再二选一，不必现在定：

| 若更想补云原生故事 | 若更想补 VPP 业务故事 |
|---|---|
| **薄切片：APISIX(+etcd) 进集群**，upstream 改成 `*.vpp.svc.cluster.local`，删 extraPortMappings，关掉 NodePort 旁路 | **Phase B：Forecast v1（同比/移动平均）+ Optimization v1（阈值规则 → SubmitTask）** |
| Casdoor 跟着走，改 `origin`/discovery | 那时再判断要不要 BFF；gateway 继续当 EMS 适配器 |
| Postgres/Kafka 仍然靠后 | 审计放到 Optimization 之后：那时任务链更长，按 TaskID 查询才有故事 |

压测 + HPA 仍放在「集群形态更干净、至少有一个可水平扩展的服务（simulator / alarm 查询面）」之后，不要为了压测去迁 Kafka。

## 一句话决策标准

- **还缺业务闭环、缺「第七个服务」、缺把已有事件用起来** → 告警。
- **还缺「Ingress / 边缘 / 只有网关能进集群」** → 单独做 APISIX 进集群，不要和告警并行铺开。
- **还缺「这是虚拟电厂而不只是微服务脚手架」** → 告警之后再 Forecast + Optimization，不要现在。
- **审计**是告警的超集，现在做会抢同一条故事线。

如果认可这个方向，下一步适合先写一份告警的范围说明（消费哪些 event type、领域模型、查询 API、kind 怎么挂），再动手；我这边是 Ask 模式，只能帮你把范围和接口边界钉死，改代码需要切到 Agent 模式。
