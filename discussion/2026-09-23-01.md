# Optimization 规则从哪来，以及点名、角色该归谁

> 本文是一次讨论的备忘录，供下一次改 Optimization / Resource / Gateway 时接着用，不是实现方案，也还没有改代码。起点是 `internal/optimization/domain/model/rule.go` 里关于「等 Resource 公开点的角色后再做自动发现」的注释。

---

## 一、v1 现在实际在做什么

Optimization v1 不是求解器，也不是 Alarm 那种只观察的监控。它是一个按周期看当前值、越限就下发的闭环控制器：`DecisionLoop` 对配置里的每个租户跑一轮，`Evaluator` 对每条启用的 `SOCThresholdRule` 调 Telemetry `GetSnapshot`，越限则 `SubmitTask`（`TriggerType=automatic`）。名字来自路线图里的决策层（以后接预测、分摊、市场）；v1 只做了其中最小的一块，SOC 阈值。

拉哪些 CU 不是服务自己发现的，也不是拉舰队快照再筛选。名单在 `config/optimization.yaml`：

- `tenant-ids`：每个周期跑哪些租户。空则空转。
- `rules.soc-thresholds[]`：每条规则自带 `cu-code`、`read-point-key`、`write-point-key`，以及 `min-soc` / `max-soc` / 充放电功率 / 冷却时间。

`Evaluator` 用 `rule.CUCode` 取快照，用 `rule.ReadPointKey` 从 `Snapshot.Metrics` 里取 SOC。没有这条规则的 CU 不会被读、也不会被评估。默认两段都是空的。

这是有意的 v1 占位（设计方案照抄 alarm：规则先放配置，等业务稳定再外置），不是长期形态。业务策略不该跟着部署文件走，改一次阈值不该重新发版。

---

## 二、一次决策其实要三样东西

| 需要什么 | 例子 | 现在在哪 |
|---|---|---|
| 当前值 | 这台 CU 的 SOC 是 15 | Telemetry 快照。必须已经知道键名 |
| 键的含义 | 快照里哪个字符串是 SOC，哪个是功率设定 | 没有。YAML 手写 `read-point-key` / `write-point-key` |
| 策略数字 | 20% / 90% / 50 kW / 冷却时间 | YAML。不是遥测，也不是设备铭牌 |

Telemetry 只能稳定提供第一行，而且只在调用方已经知道字符串键的前提下。`GetSnapshot` 返回的是 `map[string]float64`，键是接入时带来的指标名。快照里没有运行界限。`QueryAggregation` 的 MAX/MIN 是时间窗里出现过的极值，不是允许运行的上下限。Telemetry 自己的边界是只认 `(TenantID, CUCode)`，不解释名字（模拟量只更新数值，阈值策略不在这里）。

所以「Optimization 从 Telemetry 拿状态，再拿 max/min，然后执行逻辑」在现有模型上走不通：界限不是测量值。

策略数字（低于多少充、充多少）属于 Optimization 自己的业务数据。以后应进 Optimization 的库，按租户用 API 改，而不是继续放在 `optimization.yaml`，也不要放进 Resource。YAML 只留进程参数：决策周期、上游地址、熔断。

设备安全限（SOC 不许低于 5%、最大充电功率）是另一件事，更像资产约束。Resource `Point.SafetyThresholds` 已经留了这类字段（如 `min_soc` / `max_power`），Optimization 没有用。安全限和运行策略不要混成一个字段。

## 三、Resource 的 Point 和 Telemetry 的键现在没有关系

Resource 的 `Point` 是目录：`PointKey`、数据类型、`ControlFlag`、`ExternalAddress`、可选的 `SafetyThresholds`。三级 Runtime 缓存（`AssetRuntime` / `CURuntime` / `PointRuntime`）本来想给前端放最新值，写路径是空的，Resource 里现在没有运行时数值。详见 `architecture.md` §3.3.1。

运行时数值只在 Telemetry。Gateway 把外部设备 ID 译成 `CUCode`，指标名原样转发，不查 Resource，也不按 `PointKey` 改名。Telemetry 代码里没有 `PointKey` 这个字段。

因此两边可以各写各的：Resource 里是 `bms.soc`，快照里是 `soc`，系统不会报不一致。Optimization YAML 里的 `read-point-key` 只是借用了 Resource 的词，读的是 Telemetry 的 metric name。

Simulator 是唯一把两边写成同一个字符串的地方：上报时用自己的 `PointKey` 填进 `metrics[].name`。那是模拟器自己的约定，不是 Resource 和 Telemetry 之间的契约。

## 四、已对齐的方向

**内部键统一成一个字符串。** Resource 的 `PointKey`、Telemetry 快照的 metric name、Dispatch 下发时的 `PointKey`，三者应是同一个值。Optimization 读 SOC、写下发功率，用的也是这个值。设备侧的寄存器名、厂商点名不要并进这套名字，留在 Point 已有的 `ExternalAddress` 上。

**翻译发生在 Gateway 接入。** 和今天把外部设备 ID 译成 `CUCode` 一样，外部点名进来时换成内部 `PointKey`，之后 Telemetry 里只会看到内部键。这一步现在没做。

**角色放在 Resource 的 Point 上。** 例如 `soc`、`active_power_setpoint`。角色是目录记录的语义标签，不是测量值，也不是充放电策略。Telemetry 不该知道「这个键是 SOC」。Optimization 不保存第三套名字：按角色向 Resource 要 `PointKey`，再用这个键去 Telemetry 读、向 Dispatch 写。

角色能工作的前提，就是上面的内部键已经统一。现在没有这条约定，所以还不能只加一个 role 字段就当自动发现已经成立。

**策略继续属于 Optimization。** 一条策略大致是：`tenant_id`、`cu_code`、`enabled`、SOC 上下限、充放电功率、冷却时间。不再手写读/写点名。`tenant-ids` 也可以改成「库里有启用策略的租户」。

决策循环因此变成：读自己的策略 → 向 Resource 按角色解析 `PointKey`（可缓存）→ `GetSnapshot` → 现有 evaluate / 冷却 / `SubmitTask`。后面三段不用改。

---

## 五、还没做

- Resource `Point` 增加角色；Gateway 接入时把外部点名译成 `PointKey`。
- 确认现有接入数据里，metric name 与 `PointKey` 是否已经碰巧相同；不同则要补映射，不能只加角色。
- Optimization 策略移出 YAML，进自己的存储和 API。`soc-thresholds` 整段从部署配置删除。
- `SafetyThresholds` 与运行策略的边界，在改模型时写清楚，避免把「不许低于 5%」和「低于 20% 就充 50 kW」放进同一个字段。
