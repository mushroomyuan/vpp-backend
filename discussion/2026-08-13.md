现在解释一下那些"奇怪的 docker 容器"：

那些是 **testcontainers-go 在跑集成测试时自动创建的临时容器**，不是我手动 `docker run` 出来的，是 `tests/integration` 里的 Go 测试代码在跑的时候，testcontainers-go 这个库帮你调 Docker API 拉起来的。每次跑 `go test` / `make test-integration`，你会看到这几个容器冒出来又消失：

| 容器 | 用途 | 生命周期 |
|---|---|---|
| `testcontainers/ryuk:0.14.0` | **哨兵/清道夫容器**，专门防止测试进程意外崩溃（比如你直接 kill 掉、或者 CI runner 突然没了）导致后面那些容器变成"孤儿"永远占着资源。它会监控测试进程，一旦发现测试进程退出但容器还在，就自动把它们清掉 | 整个测试会话期间常驻，测试一结束自己也退出 |
| `postgres:16-alpine` ×2 | 一个当 dispatch 的库、一个当 gateway 的库（生产环境这两个服务本来就是分开的数据库），启动时直接把 `migrations/dispatch/000001_init.up.sql` 和 `migrations/gateway/000001_init.up.sql` 灌进去，得到一个跟真实 schema 一致但全新、干净的库 | 测试跑之前起，`TestMain` 里注册的 cleanup 在整个测试套件跑完后终止+删除 |
| `confluentinc/confluent-local:7.5.0` | 单节点 KRaft 模式的 Kafka，用来跑真实的 `dispatch.publish -> gateway 消费` 和 `gateway.publish CommandCompleted -> dispatch 消费` 这两条消息队列链路 | 同上，测试完就销毁 |

日志里看到的 `🐳 Creating container` → `✅ Container started` → `🔔 Container is ready` → （跑测试）→ `🐳 Stopping container` → `🚫 Container terminated` 这一整套，就是 testcontainers-go 库自己打的生命周期日志，属于正常流程，不是什么异常或者副作用。

为什么要这么做，而不是复用你 `compose.yaml` 里已经常驻跑着的那个 Postgres/Kafka：
- **隔离**：每次测试都是全新的空库/空 topic，不会因为你本地 Postgres 里已经有别的服务写的脏数据而让测试结果不稳定，也不会测试跑完后把垃圾数据留在你日常用的开发库里。
- **可重复**：换一台机器、换到 CI 的全新 runner 上，不需要提前手动 `docker compose up`，`go test` 自己就能拉起所需的一切、跑完自己清理干净。这也是为什么我在 `.github/workflows/ci.yml` 里新增的 `integration-test` job 不需要额外配置任何基础设施，`ubuntu-latest` runner 自带 Docker，跑起来的效果和你本地一样。

顺带一提，第一次跑的时候我踩到一个坑：Kafka 容器刚启动、端口已经能连上但内部协调机制（consumer group coordinator）还没完全就绪，这时候立刻发消息会报 `Unknown Topic Or Partition`。后来加了一段"重试预创建 topic"的逻辑等它真正就绪，这也是为什么你会看到测试跑了两轮我才最终确认稳定通过。
